# 학습 가이드 (리뷰 순서)

> 이 골격은 "네가 설명할 수 있어야 하는 코드"다. 아래 순서로 읽으면 하루 저녁 두 번이면 끝난다.
> 각 단계의 질문에 소리 내어 답할 수 있으면 그 파일은 통과. 면접 질문이 곧 이 질문들이다.

## 1일차 — 계약과 모델 (전송 계층 없이)

**① `proto/fleet.proto` (15분)** — 이 프로젝트의 설계 문서.
- 왜 텔레메트리는 client stream이고 명령은 bidi stream인가? (힌트: 누가 말을 시작하는가)
- unary RPC 4번 호출과 스트림 1개의 차이는? (연결 재사용, 순서 보장, 서버가 먼저 보낼 수 있는가)
- `oneof kind`는 왜 썼나? MQTT에서라면 이걸 어떻게 표현했었지? (daijin: 토픽 이름 + flags 바이트)

**② `internal/fleet/registry.go` (20분)** — 관제의 심장.
- `Update`가 bool을 반환하는 이유는? "상태"가 아니라 "전이"를 보고하는 게 왜 중요한가?
- `Sweep`은 daijin의 무엇에 해당하나? (브로커 LWT) 왜 여기선 서버가 직접 판정하나? (브로커가 없으니까)
- `Snapshot`이 포인터가 아니라 복사본을 주는 이유는?

**③ `internal/fleet/hub.go` (20분)**
- `Send`가 버퍼 가득 찼을 때 기다리지 않고 에러를 내는 이유는? (백프레셔를 보이게 만들기)
- 재연결 시 옛 채널을 닫고 교체하는 로직 — "좀비 스트림" 문제가 뭔가?
- `Register`가 돌려주는 정리 함수에서 `h.conns[robotID] == ch` 비교를 왜 하나? (늦게 죽는 옛 스트림이 새 등록을 지우면 안 됨 — 이거 면접에서 물어보기 좋은 레이스다)

**④ `internal/fleet/registry_test.go` (20분)** — 테이블 드리븐 테스트 패턴 (crow에서 하던 그것).
- 각 케이스가 "무엇이 전이이고 무엇이 아닌가"를 어떻게 고정하는지 확인.
- 직접 케이스 하나 추가해보기: "오프라인 → Sweep 두 번 → 복귀 → 다시 침묵 → 다시 오프라인" (두 번째 오프라인도 전이 1회로 잡혀야 함)

## 2일차 — 전송 계층과 클라이언트

**⑤ `cmd/server/main.go` (30분)**
- `StreamTelemetry`에서 `io.EOF`와 일반 에러의 차이는? (정상 종료 vs 끊김)
- `CommandChannel`에서 "첫 이벤트는 반드시 Hello" 규칙이 왜 필요한가? (스트림에는 이름표가 없다 — 연결과 신원을 묶는 건 프로토콜의 몫)
- 허브 채널을 스트림으로 흘리는 고루틴 — 이 고루틴은 언제 어떻게 죽나? (`done()`이 채널을 닫으면 range 종료)
- HTTP POST /command가 409를 주는 상황 두 가지는?

**⑥ `cmd/robot/main.go` (30분)**
- 백오프가 "오래 산 세션이면 리셋"하는 이유는? (일시 장애와 반복 장애의 구분 — daijin 재접속에서도 같은 문제)
- `--flaky`는 무엇을 검증하기 위한 장치인가?
- 상태 기계에서 배터리 20% 미만이면 명령과 무관하게 CHARGING으로 가는 것 — 이런 "로봇의 자율 규칙 vs 서버 명령"의 우선순위 충돌은 실제 관제에서 어떻게 다뤄질까? (열린 질문, 면접 대화용)

**⑦ 직접 돌려보기 (30분)**
```bash
go test ./...
go run ./cmd/server &
go run ./cmd/robot --id r1 & go run ./cmd/robot --id r2 --flaky &
curl -s localhost:8080/fleet | python3 -m json.tool
curl -s -X POST localhost:8080/command -d '{"RobotID":"r1","Verb":"goto","Arg":"5,5"}'
# r2가 스스로 끊겼다 돌아오는 걸 서버 로그로 관찰 (🔴 → 백오프 → 🟢)
```

## 3일차 (선택) — 확장하며 체화

체화는 읽기가 아니라 수정에서 온다. 난이도 순:

1. **verb 추가**: `speed:n` (이동 속도 변경). proto 수정 없이 가능 — 왜 가능한지도 답해보기 (verb/arg를 string으로 둔 트레이드오프: 유연함 vs 타입 안전. gRPC답게 하려면 어떻게 바꿔야 했을까?)
2. **STALE 판정 추가**: online인데 텔레메트리 주기가 3배 이상 벌어진 로봇을 `/fleet`에 표시 (fleet_watch.py의 STALE과 같은 개념)
3. **명령 결과 조회**: POST /command가 command_id를 주니까, ACK를 registry에 저장하고 GET /command/{id}로 결과 확인
4. **daijin 연동 (데모 카드)**: 브레인의 dev.sh 옆에 fleet.sh처럼 `curl localhost:8080/fleet`을 도구로 등록하면, 다이진이 **MQTT 플릿과 gRPC 플릿을 동시에 관제**하는 그림이 나온다. 이기종(heterogeneous) 관제라는 팀 이름 그대로.

## 면접에서 나올 질문 (README의 표와 함께 준비)

- "MQTT랑 gRPC 중 뭘 쓸 건가요?" → README의 비교표가 답. 핵심 문장: "엣지의 원거리 디바이스는 브로커 랑데부(MQTT), 인프라 경계 안의 제어 평면은 타입 있는 양방향 스트림(gRPC). 실제 시스템은 보통 둘 다 씁니다."
- "스트림이 끊기면 어떻게 되나요?" → 로봇: 지수 백오프 재접속 + Hello 재선언. 서버: 스윕이 타임아웃 판정, 재등록이 좀비 스트림 교체.
- "왜 브로커 없이 만들었나요?" → 만들어봤으니까(daijin). 이번엔 반대편 트레이드오프를 몸으로 확인하려고.
